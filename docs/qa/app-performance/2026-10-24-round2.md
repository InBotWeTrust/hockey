## Находки и предложения

### 1. P1 — компактный профиль всё ещё ждёт исторических вычислений

Подтверждено: `packages/server/src/chat/service.ts:409` → `getUserPublicProfile` всегда ждёт `fetchTrophySummary`, а `readPublicProfileProgress` (`profile/summary.ts:389`) ждёт `fetchPlayStreakStats`. `profile/activityStreak.ts` читает историю сессий игрока, преобразует даты, делает distinct и оконные вычисления. Ограничение одним игроком уже есть; готового результата серии дней ещё нет.

Предложение: хранить дневную активность/сводку текущей и лучшей серии, обновлять при игровом событии; учитывать смену часового пояса, полночь, DST и исправление истории. Сводку трофеев обновлять при завершении соревнования/выдаче награды. При необходимости разнести основной профиль и вторичную статистику по независимым загрузкам.

Результат: основное чтение профиля перестанет зависеть от длины истории. Проверка: EXPLAIN ANALYZE BUFFERS и холодные/тёплые P50/P95 для нового и многолетнего игрока. Секунды ускорения пока неизвестны.

### 2. P1 — сводка трофеев начинает вычисления с общего набора финалов

`profile/summary.ts:64`: CTE `playoff_finals` строит финалы турниров, затем результаты связываются с игроком. Ограничение игроком не задано в исходном CTE. Нельзя утверждать фактический полный scan без плана PostgreSQL, но область вычисления в SQL шире необходимой.

Предложение: сначала определить турниры/участия игрока и ограничить финалы либо читать сохранённую сводку из пункта 1. Сохранить правила архивных турниров и исключения двойного подсчёта. Сравнить планы на реалистичной истории.

### 3. P1 — новая миграция счётчиков переносит нагрузку на запись

`packages/server/db/migrations/242_achievement_summary.sql`: каждое изменение завершённости вызывает пересчёт каталога для игрока; изменение каталога вызывает rebuild для всех пользователей. Rebuild держит блокировку общей строки, а обычный refresh запрашивает совместимую с другими refresh, но конфликтующую с rebuild блокировку FOR SHARE. Это не глобальная сериализация всех обычных завершений, но обновление каталога может задержать их все.

Backfill покупок выполняется после установки row triggers, затем запускается общий rebuild: часть вычислений при миграции повторяется.

Предложение: измерить массовые завершения и обновление каталога; объединять пересчёты одного игрока в пределах операции, избегать лишнего прохода backfill. Для большой базы рассмотреть версионную сводку и контролируемый пакетный rebuild. Нужны rollback/concurrency проверки, паритет счётчиков, время транзакции и ожидания блокировок. Не заменять точные счётчики приблизительными.

### 4. P1 — рейтинг статистики вычисляет общую таблицу мест дважды

`profile/statRating.ts:70`: один и тот же `ranked` строится отдельными SQL для страницы и места пользователя; затем идёт ещё запрос totals. Для streak используются общие CTE активности всех игроков. Запросы последовательные.

Предложение: возвращать страницу и место одним расчётом либо использовать версионированный снимок рейтинга. Для streak сначала агрегировать дни активности. Ограничить частоту пересборки по согласованной допустимой свежести. Проверять одинаковые места, tie-breaks и границы страниц.

Результат: меньше повторных общих сортировок и SQL round-trips. Сначала сравнить EXPLAIN для 1k/10k/100k синтетических игроков.

### 5. P1 — повторное открытие рейтинга обновляет всю накопленную пагинацию

`web/src/profile/StatRatingModal.tsx:52`, `ExperienceRatingModal.tsx:67`: `useInfiniteQuery`, `refetchOnMount: 'always'`, без `maxPages`; defaults `['profile']` имеют `gcTime: Infinity` (`app/queryClient.ts:25`). После глубокого просмотра кеш сохраняет все страницы, а повторный mount запрашивает их повторно по механизму infinite query.

Предложение: ограничить сохраняемое окно и обновлять первую страницу/снимок рейтинга, предусмотрев восстановление позиции. Не смешивать страницы разных версий рейтинга. Проверка: загрузить 20 страниц, закрыть/открыть, посчитать HTTP-запросы и проверить отсутствие пропусков/дубликатов.

### 6. P1 — длинный чат целиком остаётся в DOM

`chat/screens/ChatRoomScreen.tsx:634,1264,1459`: накопленные сообщения сортируются, фильтруются и все выводятся через `visibleMessages.map`. Локальный поиск также проходит по всему загруженному массиву. Пагинация API сама по себе не ограничивает DOM.

Предложение: виртуализация переменной высоты с запасом элементов вокруг экрана. Проверка на 2000 сообщений с фото, reply, реакциями, поиском и goto; сохранение scroll anchor при подгрузке и загрузке изображений. Результат: ограниченный DOM и меньше работы при каждом обновлении; целевые FPS требуют реального устройства.

### 7. P1 — reconnect чата может заново загрузить все старые страницы

`chat/useChatSocket.ts:282`: при открытии WS инвалидируются истории, активная история refetch; `ChatRoomScreen.tsx:559` хранит infinite pages без ограничения. Это правильная защита от пропущенных edits/deletes, но цена растёт с числом страниц.

Предложение: серверная сверка изменений по ревизии/курсору с tombstones удалений либо ограниченное окно истории и управляемая полная сверка. Просто убрать invalidation нельзя. Проверка: offline → edit/delete → reconnect, количество запросов и актуальность сообщений.

### 8. P1 — список чатов не ограничен и повторно считает unread

`server/src/chat/service.ts:105`: запрос возвращает весь список, получает последнее сообщение и unread через lateral, считает участников; перед чтением выполняет обеспечение системного канала и INSERT членства. `getUnreadCounts:986` отдельно считает непрочитанные.

Индексы сообщений уже есть (`004_chat.sql:61`); нельзя объяснять проблему просто отсутствием индекса. PostgreSQL может вычислить независимый count пользователей один раз, поэтому «count всех пользователей на каждый чат» не утверждается.

Предложение: измерить 100/1000 чатов и большой непрочитанный хвост; затем пагинация списка, переиспользование сводки unread, перенос обеспечения системного членства из каждого чтения. Сохранить auto-pin новых каналов и явный unpin. Критерий: ограниченный ответ и число операций независимо от всей истории.

### 9. P2 — подтверждённый дублирующий SQL социальной активности

### 10. P2 — предварительная загрузка картинок не ограничена по объёму запросов

Предложение: очередь с ограничением параллелизма, приоритет видимой области, отмена устаревшей очереди при уходе, загрузка следующих карточек при приближении. Проверка: большие каталоги, быстрые смены категорий, сетевой waterfall и память. Сохранить заранее подготовленный активный фон.

## Что проверено и не требует немедленного переписывания

- Карта уже удерживает только две подготовленные картинки (`cityImageCache.ts`), новый фон появляется после decode, старый слой убирается после перехода (`CityBackground.tsx`). Это не гарантия конкретного расхода GPU-памяти.
- Погода уже останавливает canvas в hidden/reduced motion, ограничивает DPR до 1.5, число частиц до 150 и частоту рисования примерно 30 FPS (`WeatherOverlay.tsx`). Повторно предлагать эти же оптимизации не нужно. Настоящее время GPU/compositing не измерялось.
- Рейтинг опыта уже использует cursor, индекс сортировки частично есть (`128_experience_rating_index.sql`). Проверять нужно соответствие выражению accuracy и цену места текущего игрока, а не безусловно добавлять ещё индекс.
- Компактный профиль уже не запускает grant achievements. Старые full API сохраняют repair для совместимости; удаление требует проверки клиентов и всех событий начисления.
- Общие query keys и in-flight dedup уже есть. Количество setInterval в исходниках само по себе не равно числу сетевых запросов.
- В nginx конфигурации этого пакета gzip не указан. Сжатие может выполнять внешний proxy: отсутствие Content-Encoding на dev/prod не установлено, отключённое сжатие не объявляется находкой.
