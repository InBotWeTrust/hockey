## Новые находки (продолжение предыдущих 16)

### 17. P1 — пустые фоновые очереди драк опрашивают SQL каждые 10 мс

`server/src/duel/amateur/fight/worker.ts:69–86`: два интервала 10 мс, каждый вызывает запрос до проверки наличия работы. `fight/outbox.ts:5` читает pending outbox. `app.ts:265` включает worker по умолчанию вне test. Защита running/publishing предотвращает overlap одного цикла, но не отменяет пустые чтения.

Потенциально до 100 + 100 первоначальных SELECT/с на процесс при быстрых ответах. Это теоретический потолок по коду, не снятый pg_stat_statements. При нескольких процессах нагрузка умножается. У активного in-memory FightRuntime отдельный 10мс tick — его нельзя автоматически замедлять вместе с обслуживанием БД.

Предложение: сначала измерить empty/active QPS; для пустого outbox и legacy deadline scan — пробуждение событием/следующим deadline с fallback и backoff. Сохранить скорость боевой симуляции, lease, replay, outbox delivery. Проверка: задержка команд и публикаций, crash/recovery, несколько серверов.

### 18. P1 — история ежедневных игр имеет последовательный N+1

`server/src/duel/daily/routes.ts:233–267`: после получения страницы для каждой записи отдельно читаются периоды и отдельно суммируются те же period_log. Для 20 записей это 40 дополнительных SQL только в цикле; до/после него есть другие запросы.

Предложение: один batch периодов по ID страницы, итоги вывести из уже прочитанных периодов либо одним GROUP BY. Ожидаемый результат: число обращений станет постоянным относительно размера страницы. Проверка: паритет totals/duration/неполных периодов и SQL query count. Механику броска менять не требуется.

### 19. P1 — тяжёлое обновление турниров стоит в пути GET

`server/src/tournament/routes.ts:268,398,415,484,501,516` ждёт `reconcileTournamentLifecycleBestEffort`. `plugins/tournamentLifecycle.ts:42` дополнительно ждёт восстановления missing series games. Отдельный periodic tick защищён activeTick, но метод для чтений не разделяет эту защиту; параллельные запросы разных вкладок могут повторить работу. `automaticLifecycle.ts:688` последовательно обходит турниры.

Предложение: shared in-flight reconcile по турниру + ограничение списка затронутым турниром, затем перенос фонового обслуживания в worker с явно определённой свежестью. Проверять переходы расписания и выдачу наград; нельзя просто удалить reconcile и получить устаревшие состояния.

### 20. P1 — каталог челленджей пересчитывает историю по одному заданию

`server/src/weeklyChallenge/service.ts:65,170,250`: каталог без LIMIT; каждый candidate последовательно вызывает mapChallenge, а он отдельно читает tasks, reward и прогресс за временной диапазон. Аналогичный обход есть для pending rewards и failures.

Batch расчёт истории трофеев из первого этапа этот каталог не покрывает.

Предложение: пагинация завершённых, batch tasks/rewards/progress, сохранение финального результата закрытого челленджа. Проверка 100/1000 старых заданий, SQL count и совпадение условий доступа/наград.

### 21. P1 — обязательный preload игры крупнее самого кода игрового экрана

`web/src/game/PixiStage.tsx:6–23,61`: перед onReady загружается общий набор из 14 спрайтов, включая оба хвата и обслуживание льда. Измерено 1,60 МБ файлов и около 57,4 МиБ RGBA-пикселей. Это ещё без дополнительных preloadAssets.

Предложение: определить обязательный набор текущей сцены/хвата, остальное подготавливать по следующему сценарию. Не ломать Assets.load/cache и первый кадр, не удалять текстуры используемой сцены. Проверка cold game ready, последующая анимация падения/заливки и отсутствие повторных скачиваний.

### 22. P1 — Range-запрос медиа всё равно скачивает файл целиком на backend

`server/src/storage/objectStorage.ts:224–245`: await res.arrayBuffer → Buffer. `routes/media.ts:265–287`: byte range выделяется уже после загрузки полного объекта. Так маленький запрос аудиодиапазона может стоить серверу целого файла; параллельные чтения увеличивают память и исходящий storage traffic. Upload тоже buffer-based, лимиты до 25 МиБ.

Предложение: передавать Range в object storage и стримить тело с backpressure, отменой и timeout. Либо безопасная подписанная delivery URL с сохранением контроля доступа. Не делать приватные медиа публичными ради скорости. Проверка диапазонов/416, отмены, размера памяти при 10–50 клиентах.

### 23. P1 — фоновые проверки достижений daily не объединяются по игроку

`duel/daily/routes.ts:562` запускает recovery после state/history/действий. `completionSideEffects.ts` хранит Set обещаний, но не объединяет одинаковые задачи и не ограничивает concurrency. `achievements/engine.ts:295` повторно ищет period_closed без evaluated в event_log и обрабатывает их последовательно.

Предложение: одно выполняющееся восстановление на игрока + устойчивый журнал заданий/водяной знак; семантику exactly-once reward сохранить существующими транзакционными защитами. Измерить число recovery при параллельном state/history и большом backlog.

### 24. P2 — сводка навигации дуэлей делает транзакционную работу по матчам

`duel/amateur/routes.ts:5683`: events выбирает до 10 матчей, блокирует получателей наград, создаёт savepoints, делает reconcile и build DTO по каждому. Этот endpoint опрашивается навигацией каждые 15 секунд.

Предложение: отдельная лёгкая сводка индикаторов или материализованная activity-сводка, с authoritative read при открытии площадки. Не кешировать старый разрешённый бросок и не изменять merge текущего match state. Проверить масштаб 0/10 матчей и contention с командой броска.

### 25. P2 — магазин смешивает общий каталог и все пользовательские экземпляры

`routes/inventory.ts:438–544`: ensure rows, settings, account, полный каталог четырёх видов со всеми instance joins, затем visitor card. Всё последовательно; нет разделения статического каталога и динамического состояния. `InventoryScreen.tsx:184` также получает receipt email до открытия банка.

Предложение: версионированный кеш каталога, компактные balances/equipment/owned items, получение email по открытию платежного интерфейса. Разделить read initialization и обычное чтение. Проверка больших коллекций, покупки/экипировки/резерва ресурсов; не ослаблять транзакции покупки.

### 26. P2 — вспомогательные экраны всё ещё требуют полный /me

`LockerRoomScreen.tsx:24`, `ProfileDestinationScreens.tsx:45,146,187`, `ProfileStorySeriesScreen.tsx:10`: читают полный профиль. Replay серии специально требует свежий ответ и ждёт isFetchedAfterMount. Этот путь способен вернуть старую тяжёлую загрузку после облегчённой карты.

Предложение: специализированные компактные DTO экипировки/доступа к сюжету, обновляемые по событиям. Для сюжетного доступа сохранить серверную проверку. Проверить переходы карта → раздевалка/сюжет → карта, пустой/тёплый кеш.

### 27. P2 — история разговора персонажа хранится и возвращается цельным JSONB

`bar/conversationStore.ts:26,127`: read получает все turns, complete дописывает JSONB и возвращает весь массив; reserve тоже читает массив. Memory summary сокращает контекст модели, но не отменяет эту стоимость хранения/ответа.

Предложение: отдельные сообщения с курсором, короткий хвост в UI/LLM и сохранённое summary. Проверить 100/1000/10000 реплик, длительность UPDATE и bytes ответа. Сохранить revision/idempotency, историю для пользователя, forget/reset/generation fences.

### 28. P2 — медленный платёжный провайдер занимает соединение общего DB pool

`payments/service.ts:50–180`: checked-out client и session advisory lock удерживаются на время provider.createPayment. Таймаут провайдера уже есть (`yookassaClient.ts:124`), длинной DB-транзакции вокруг HTTP нет — это положительная защита. Но свободное соединение всё равно занято внешним ожиданием; `plugins/db.ts` использует общий pool без индивидуального budget этого пути.

Предложение: измерить pool wait при медленном mock provider, ограничить concurrency создания платежей; при необходимости durable state + lease вместо удержания session lock. Не убирать idempotency и не начинать начислять деньги на create. Проверить crash/retry/двойное создание до изменения архитектуры.

### 29. P2 — общие HTTP-запросы не имеют явного прикладного deadline

`web/src/api/apiFetch.ts:172–204`: передаёт signal только если его дал caller; refreshOnce общий, но runRefresh без deadline. `storage/objectStorage.ts` также не задаёт timeout для GET. При зависшем ответе пользователь может видеть ожидание до сетевого timeout платформы.

Предложение: отдельные timeout-политики для read/refresh/upload, отмена устаревших чтений при уходе; мутации после timeout должны сверяться с сервером по idempotency key, а не слепо повторяться. Это улучшение предсказуемости ожидания, не обещание более быстрого успешного запроса.

### 30. P2 — административная аналитика конкурирует с пользовательскими запросами

`admin/routes.ts:2540`: одновременно выполняются общие totals, push stats и несколько аналитических наборов. Во frontend большинство вкладок правильно gated; attention обновляется каждые 15 секунд. Отдельного кеша общего dashboard в этом обработчике нет.

Предложение: короткий кеш по периоду, предагрегаты дневных метрик, измерение DB pool wait при открытии админки. Не масштабировать pool вслепую и не объявлять любой Promise.all проблемой. Приоритет зависит от частоты использования админки.

## Что не предлагается менять без доказательств

- Активный fight runtime, серверные часы и частоту отправки команд; отдельный SQL worker нельзя путать с самой симуляцией.
- Транзакционные блокировки покупки/награды: они защищают от двойных списаний и гонок. Оптимизировать длительность/область, сохраняя инварианты.
- Push уже использует ограниченный batch, concurrency и skip locked; memory jobs имеют leases и ограниченный batch. Их наличие само по себе не дефект.
- В погоде уже есть часовой freshness, in-flight dedup, timeout и stale fallback. Не нужно увеличивать число запросов.
- Игровой loop корректно удаляет ticker callback при detach; Player хранит загруженные текстуры и не создаёт новую Texture на каждом кадре. Без GPU-профиля переписывание этих частей не оправдано.
- Холодная картинка после появления навигации — наблюдение стадий готовности, не автоматически промах HTTP-кеша. Нужен filmstrip/resource trace для вывода о причине.

- Запущена тренировка, выполнен один бросок, проверено повторное включение кнопки и выход на карту. После выхода ежедневная площадка показала игровое восстановление около часа. Таймеры и состояние аккаунта вручную не сбрасывались.
- Запущены шашки с Арсеничем; затем через штатные «Выйти из партии» → «Сдаться» партия завершена с результатом «Поражение», выполнен возврат в бар и на карту. Это проверка запуска/выхода, не полной игровой логики шашек.
- Реальных платежей, вызовов другим игрокам, сообщений, смены профиля, push-рассылок и административных записей не было. Production не менялся.

## Приоритет реализации

1. Исправить измерение click-to-ready из предыдущего отчёта; снять pg_stat_statements/pool wait на dev под согласованной нагрузкой.
2. Проверить/убрать пустую частую SQL-работу worker без изменения боевого tick. Устранить N+1 daily history и каталога челленджей, повторный social SQL.
3. Закончить read-модель профиля, сводки трофеев/серий и навигационных индикаторов; проверить цену триггеров счётчиков и lifecycle турниров.
4. Сократить обязательные игровые assets; разнести тяжёлые route modules, ограничить preload очереди. Проверить первый кадр и возврат.
5. Длинные чаты/рейтинги: ограничение DOM и страниц, безопасный reconnect; барная история с cursor.
6. Streaming медиа, бюджеты внешних запросов/пула, аналитика и PWA quota.

Для каждой оптимизации требуются RED/GREEN по изменённому поведению, паритет данных и измерение одной и той же нагрузки до/после. Ускорение «в N раз» без этих измерений не обещается.

## Оставшаяся граница аудита

Теперь есть обследование остальных основных подсистем и реальный авторизованный обход dev с выбранными игровыми/покупочными действиями. Но это всё ещё не полная приёмка каждой ветви приложения на всех устройствах.

Остаются: реальные cold/warm P50/P95 профиля и переходов, SQL EXPLAIN на реалистичных данных, idle QPS серверных workers, 2000-message fixture, длительная игровая сессия двух клиентов, все bonus/bar режимы, физический Android/iPhone, mobile heap/FPS, offline/quota PWA и тестовые сценарии платёжного провайдера. Без них нельзя честно утверждать, что всё приложение работает быстро или что все узкие места обнаружены.

Изменений production-кода, новых коммитов и деплоев в этом аудите нет. Существующие тестовые результаты из предыдущей работы не выдаются за новый запуск. Локальная ветка реализации сохранена без правок.
