# Драки в обычных дуэлях — план реализации

> **Для исполнителя:** выполнять по этапам через `superpowers:executing-plans`. Делегирование и изменение настроек модели этим документом не разрешаются. Чекбоксы отмечать только по фактическим результатам.

**Цель:** добавить добровольную серверную мини-игру драки в обычную дуэль с общей паузой, честным разменом ударов, однократными наградами и безопасным возвращением в хоккей.

**Архитектура:** чистый движок в game-core; сохраняемое состояние, команды и обработчик deadlines на сервере; отдельный игровой WebSocket и Pixi FightView на клиенте. PostgreSQL определяет состояние и результат, Redis доставляет уведомления. Потерянные уведомления восстанавливаются snapshot-запросом.

**Стек:** существующие TypeScript, pnpm, Fastify, PostgreSQL, Redis, React/Zustand, Pixi и Vitest. Новые runtime-библиотеки не нужны.

**Спецификация:** продуктовый контракт ниже объединяет исходный запрос пользователя от 06.10.2026 и последующие согласованные ответы в этом чате. Исходный текст: `/Users/egorgumenyuk/.codex/attachments/7a6f2003-8163-4d04-a20d-23b58fdc6ef5/Вставленный текст.txt`. Контракт в этом документе самодостаточен для реализации.

## 1. Ограничения и исходное состояние

- Только `source = challenge | matchmaking`. Любой `tournament`, регулярный этап, плей-офф, daily, training и bonus games исключены сервером и UI.
- Node >=20, pnpm >=9. Код, комментарии и commit messages на английском; пользовательский UI на русском.
- Анализ выполнен по локальному `dev`, HEAD `04c10cd0887ae4a1fd740f3d99d00ddb6b89cf2e`. Свежесть относительно remote не подтверждалась. Checkout содержит чужие изменения; их сохранять.
- Перед реализацией обновить `origin`, сверить актуальный код и базу, создать `feature/ordinary-duel-fights` от текущего `origin/dev`. При занятости checkout использовать изолированный worktree по правилам AGENTS. Не stash/reset чужие изменения.
- Этот план не разрешает deployment, production mutations, изменение аккаунтов/авторизации или запуск интеграционных тестов на обычной БД.
- Прямой XP за результат обычной дуэли в изученном settlement отсутствует. Сохранить существующую экономику: награда драки независима, новый XP за саму дуэль не добавлять.
- `users.xp` хранит звёзды; `users.experience` хранит опыт. Отдельный результат драки не меняет голы, рейтинг и победителя хоккейной дуэли.
- Текущие личные периоды работают от timestamps, общая пауза отсутствует; snapshot опрашивается раз в 2 секунды. Существующая защита store по прогрессу бросков недостаточна для драки.

### Приоритетные риски ревью

1. Новый бой или ревизия не должны теряться из-за старого poll/ответа броска — этап 6.
2. Пауза не должна расходовать питание/коньки или портить время, используемое для сравнения результатов — этап 2.
3. Рестарт/несколько серверов не должны терять принятые действия или оставлять общую паузу — этап 5.
4. Два таба одного аккаунта и повтор пакета не должны давать два действия/награды — этапы 3–5.
5. Отсутствующий спрайт/медленная загрузка не должны оставлять игрока без управления — этап 7.

## 2. Продуктовый контракт

### Доступность, вызов и возвращение

- Максимум одна успешно созданная попытка на дуэль, общая для двух игроков. Неуспешная проверка доступности попытку не расходует.
- Оба имеют не менее 30 000 мс личного активного времени за текущую дуэль, включая текущий период; оба в `period_active`, не завершили свою часть, нет общей/системной паузы.
- Нет запрета последних секунд периода. На точной границе окончания периода сначала выполняется reconcile, затем проверка вызова.
- Дополнительно проверить обоих по существующим gameplay locks и допустимость продления до турнирной границы. Если максимальное продление недопустимо — запретить вызов с понятной причиной.
- Создание вызова атомарно останавливает активные часы обоих. Ответ — 3 000 мс; на deadline и позднее действует автоотказ.
- Отказ/timeout: без наград и статистики поражения; вызванному 2 000 мс восстановления, инициатору ничего. Попытка остаётся потраченной.
- Принятие: общая подготовительная фаза 1 000 мс, затем одинаковый серверный старт. Подготовка не входит в 15 секунд боя.
- Восстановление после поражения — 5 000 мс. Личные хоккейные часы уже идут, сервер запрещает броски; перезагрузка не сбрасывает deadline. Не замораживать период ради восстановления.
- Если период закончился до recovery, следующий период не получает новый полный штраф: сервер сохраняет первоначальный deadline. Это временный запрет действия, а не долг на будущие периоды.
- Результат показать неблокирующим уведомлением на 1 500 мс поверх возобновлённой дуэли; управление победителя доступно сразу. Срок восстановления идёт независимо от уведомления.

### Бой и баланс

| Настройка | Значение v1 |
| --- | ---: |
| Стартовое HP | 3 |
| Урон чистого удара | 1 |
| Основное время | 15 000 мс |
| Sudden death | 10 000 мс |
| HP в sudden death | 1 |
| Windup | 150 мс |
| Active window | 200 мс |
| Recovery удара | 400 мс |
| Блок | 700 мс |
| Recovery блока | 350 мс |
| Шаг обработчика | 10 мс |
| Максимальная компенсация доставки | 150 мс |

- Один боец выполняет одно действие целиком, включая recovery. Новые вводы отклоняются, очереди нет. Удар занимает 750 мс, блок — 1 050 мс.
- Тап по голове/корпусу соперника атакует соответствующую зону; по своей голове/корпусу ставит соответствующий блок. Нет перемещения, удержания, свайпов и комбо.
- Блок активен сразу с начала действия. Урон проверяется один раз в начале active window удара. Поздний блок не меняет уже проверенную защиту.
- Экипировка, уровень, покупки и ресурсы не влияют на бой. Получение урона не прерывает действие и не создаёт дополнительный stun; `fight_hit` — визуальный эффект.
- Чистые удары с пересекающимися active windows применяются вместе. Нельзя объявить победу по первому из них до закрытия пары.
- Одиночный нокаут заканчивает бой после серверного подтверждения. Двойной нокаут в основном времени сразу переводит в sudden death с 1 HP обоим.
- После 15 секунд: неравный HP — победитель с большим HP; равный — sudden death. В sudden death двойной нокаут возвращает обоим 1 HP без продления deadline.
- При переходе в sudden death завершить действия предыдущей фазы и их recovery; новая фаза начинается с нейтральных бойцов. Принятые пакеты старой фазы не переносить.
- Истёк sudden death без победителя — `cancelled`, без наград и восстановления. Попытка потрачена; учитывать отдельно как отменённый бой. «Проведённые» = только бои с победителем, их число равно wins + losses.
- Отключение не отменяет бой и не создаёт отдельного штрафа. Серверные часы/действия продолжаются; подключённый соперник может выиграть. Оба отключены — действуют обычные deadlines и отмена при отсутствии победителя.
- Любой результат: победителю +1 звезда/+1 опыт/+1 win, проигравшему +1 опыт/+1 loss; только однократно. Отмены/отказы не получают награды.
- Конфиг типизирован, валидируется на сервере, фиксируется snapshot и версией при создании challenge. Настройки v1 не меняются у начатого боя.

### Временная модель и границы

Интервалы полуоткрытые `[start, end)`. Время в целых миллисекундах; периодический шаг 10 мс обслуживает deadlines, но не округляет timestamps действий. Не использовать клиентский timestamp как основание backdating.

Сервер измеряет RTT собственными WS ping/pong на игровом соединении: до доступности вызова минимум 3 замера, затем раз в секунду, хранить последние 10. Для бойца фиксировать при старте `deliveryCompensationMs = min(150, floor(minRTT / 2))`. При нехватке замеров значение 0; reconnect не увеличивает зафиксированную компенсацию. Поддельно задержанный pong может увеличить оценку, поэтому это ограниченная эвристика, а не доказательство реального времени тапа; верхний предел одинаков у обоих.

Входной пакет: идентификатор фазы и действия, сквозной sequence бойца, вид действия и зона. Сервер назначает время из момента приёма минус фиксированная компенсация. Время ранее начала фазы, уже закрытой шкалы или предыдущего действия недопустимо; не подгонять его автоматически под разрешённый момент. При перегрузке сервер может отказать действию, но не переигрывать подтверждённый HP. Задержка клиента сверх фиксированной компенсации остаётся ограничением модели.

Начатый удар A задаёт окно `[hA, eA)`. Его группу закрывать по `eA`. Все допустимые удары соперника с началом active window внутри этого окна входят в группу; при текущем recovery их может быть максимум один. Если предшествующий удар соперника пересекается с A, они уже принадлежат его группе. Блок для каждого проверять по состоянию в его собственный момент h. Пара получает урон одним переходом, без промежуточного KO. Блокированный удар не наносит урон; отдельного бонуса за блок нет.

Группа подтверждается после `groupCloseAt + 150 мс`, на следующем шаге worker. В обычном случае задержка подтверждения до 350 мс после первого контакта плюс до 10 мс шага и время обработки. Это целевой предел при нормальной нагрузке, не сетевой SLA. Поздний непринятый ввод не изменяет закрытую группу.

В конце фазы обрезать groupCloseAt её deadline. В основное время входят только удары с `h < 15 000`; попадание ровно в 15 000 не входит. Сначала закрыть группы до deadline, затем сравнить HP. Размен с ударом, чьё h уже за deadline, не создавать. Аналогично закрыть sudden death.

Начало следующей фазы и возобновление хоккея назначать при фактическом подтверждении перехода сервером, не задним числом. Таким образом sudden death получает полные 10 секунд. Пауза дуэли включает техническое ожидание подтверждения. Максимальный нормальный запас для проверки турнирной границы: `3 000 + 1 000 + 15 000 + 10 000 + 2 × (150 + 10) = 29 320 мс`; два окна нужны для перехода в sudden death и его закрытия. Прежняя оценка 29 секунд описывает игровой бюджет, а не весь срок обработки.

Примеры регрессий:

| Ввод | Ожидаемый результат |
| --- | --- |
| A начинает в 1000, B в 1100 | Active `[1150,1350)`/`[1250,1450)`; две чистые атаки дают по 1 урона одновременно |
| Правильный блок начинается в 1150 | Удар A закрыт |
| Правильный блок начинается в 1160 | Удар A проходит |
| Блок заканчивается в 1150 | Удар A проходит |
| Active B начинается в 1350 | Нет пересечения с active A |
| У обоих 1 HP, окна пересекаются | Основное время → sudden death; sudden death → обоим 1 HP, срок тот же |
| hA=14900, hB=14990 | Учитываются оба до сравнения HP |
| hA=14900, hB=15000 | Второй удар не входит в основное время |
| Старый пакет приходит после смены фазы | Отклонение, новый бой/HP не изменяются |

## 3. Данные, интерфейсы и надёжность

### Часы и состояние

Добавить общую вычисляемую модель часов обычной дуэли: накопленное время текущего периода, начало текущего активного отрезка, общую паузу и накопленную длительность пауз. Существующий `active_duration_ms` завершённых периодов не превращать в постоянно изменяемый счётчик: это вызовет двойной учёт при закрытии периода.

Один helper рассчитывает elapsed текущего периода, суммарное активное время, remaining, допустимость броска и deadlines. Использовать его при reconcile, закрытии периода, создании DTO, проверке tapTime, инвентаре, условии 30 секунд и сравнении результатов. Бросковые данные/seed/индексы сохранять при паузе; после возврата переустановить оба часовщика рендерера по authoritative snapshot. Восстановление блокирует input, но не активные часы и существующие правила расхода ресурсов.

Создать additive migration со следующими сущностями:

- `amateur_duel_fight`: UNIQUE(match_id), участники, инициатор, status (`offered`, `starting`, `fighting`, `sudden_death`, `resolved`, `declined`, `cancelled`), deadlines, rules snapshot/version, snapshot движка, ревизия, результат/причина.
- `amateur_duel_fight_command`: actionId, fightId, userId, phaseId, seq, тип/зона, серверное время приёма, effectiveAt, сохранённый ответ; UNIQUE(fightId,userId,seq) и UNIQUE(fightId,userId,actionId). Повтор ID с иным payload — конфликт, без изменения состояния.
- `amateur_duel_fight_reward`: UNIQUE(fightId,userId), stars/experience/win/loss deltas. Источник статистики — журнал результатов; отдельные агрегированные user counters в v1 не нужны.
- Сохраняемый outbox событий, отправка только после commit, retry до доставки. События идемпотентны по eventId/revision.
- Поля часов/общей паузы, `recovery_until` участника, монотонная `state_revision` матча. Каждая успешная мутация/таймерный переход увеличивает ревизию; чтение само по себе не увеличивает.

Поддержать матчи без новых полей и без fight. Непоставленные клиенты не должны молча продолжать игру при pause: availability вызова зависит от подтверждённой поддержки fight protocol обоими клиентами. Проверка — через авторизованный игровой WS; при отсутствии поддержки кнопка сообщает недоступность. После принятия обрыв соединения не отменяет бой. Не менять существующую авторизацию, аккаунты или credentials.

### Минимальные API

- REST `POST /duel/amateur/matches/:matchId/fight/challenge` с requestId; серверная проверка и возврат snapshot.
- REST `POST /duel/amateur/matches/:matchId/fight/respond` с fightId, requestId, decision `accept|decline`; повтор своего принятого решения возвращает прежний ответ, противоречивое решение — конфликт.
- Игровой WS `/duel/amateur/matches/:matchId/ws`: авторизация и membership как в REST; команды `fight:action`, ответы `fight:ack`, уведомления `duel:snapshot`, `connection:ready`; доступ только к своей паре. Не смешивать с chat delivery flags.
- Существующий GET match дополнить clock snapshot, revision, fight, recovery и availability `{allowed, reason, remainingMs}`; он же восстанавливает состояние после reconnect. Снимать snapshot под тем же порядком блокировок, что мутации.
- Fight snapshot: fightId, phaseId, status/revision, rules, serverNow, deadlines, HP, действия/recovery обоих, результат и reward summary. Дуэль сохраняет отдельные me/opponent clocks и pause reason.
- Ошибки: неверный ввод 400; чужой матч 403; несовместимое состояние/старый seq/занятость 409. Возвращать машинную причину отдельно от русского сообщения UI. Потерянный ответ требует reconciliation, а не новой команды с новым ID.

### Конкурентность и восстановление

Входные команды сначала сохранять как принятые к обработке, а не немедленно объявлять успешным ударом. Приём команды и продвижение watermark сериализовать одной блокировкой fight, используя серверное время, полученное внутри этой границы. Это определяет «получено сервером» для deadline: находившийся в очереди сетевой callback не является уже принятой командой. Worker учитывает весь committed inbox до watermark, затем закрывает его. Не разрешать финализацию между проверкой и сохранением ввода.

Сохранять существующий глобальный порядок gameplay locks → match → fight/participants → users в стабильном порядке → reward записи. Проверить реальные пересекающиеся пути перед реализацией; новый worker использует тот же порядок. Не брать fight row первым, если далее требуется match/gameplay lock.

Два вызова сериализуются: первый допустимый создаёт challenge, второй возвращает уже созданное состояние. Accept/decline/timeout — только один переход из offered. Повторные события не создают новых результатов. Серверное receipt на deadline означает timeout; не использовать время клика пользователя.

Worker запускается с приложением, опрашивает due fights каждые 10 мс и продвигает сохранённую шкалу; redis используется только для доставки. При нескольких экземплярах одна транзакционная граница выполняет переход, остальные перечитывают состояние. На старте подобрать незавершённые fights. После длительного downtime воспроизвести committed действия и deadlines; новые пользовательские фазы не должны получать бесконечное продление из-за рестартов. Если основные 15 секунд и весь дополнительный срок уже прошли по сохранённым deadlines без решающего попадания, отменить бой и возобновить дуэль. При таком recovery использовать документированную серверную timeline, не запускать новый полный бой.

Награда, результат, статистическая запись, снятие pause и выставление recovery — одна транзакция. Только INSERT успешной уникальной reward записи разрешает изменение баланса. Клиентское получение события не влияет на commit наград. Outbox и повтор snapshot не повторяют reward.

В нормальной работе продлевать общий срок матча на фактическую паузу; во время незакрытой паузы reconcile не выполняет window_end только из-за исходного ends_at. Системные ограничения остаются приоритетными. При неожиданной новой обязательной блокировке, отсутствовавшей при вызове, безопасно отменить незавершённый бой без наград/штрафа, снять pause, затем применить существующее ограничение дуэли. Это аварийное правило, а не способ разрешать заведомо конфликтующий вызов.

## 4. Этапы реализации и проверки

Для каждого этапа: сначала тест с точным ожидаемым поведением → наблюдаемый RED → минимальная реализация → GREEN → регрессии → review diff → отдельный тематический commit. Отсутствующая тестовая инфраструктура или skipped интеграция не считаются RED/GREEN. Сам план тестами ещё не проверен.

## 5. Готовность и статус плана

### Дополнительные предложения этого плана

Следующие детали предложены при составлении плана, а не отдельно подтверждены в обсуждении: сброс действий/recovery при переходе фазы; сохранение исходного recovery deadline при окончании периода; уведомление результата 1 500 мс; RTT-формула и 0 fallback; требование поддержки протокола обоими клиентами; аварийная отмена при неожиданной обязательной блокировке; восстановление после полного downtime. При ревью плана проверить их явно. Они не разрешают исполнителю самостоятельно менять согласованные награды, штрафы или победителя.

Готовность означает выполнение исходных критериев с согласованным исключением: отмена без победителя после 10 секунд sudden death. Ни один результат/награда не определяется клиентом; единичный timeout/повтор/restart не создаёт второй бой или reward; общая пауза снимается автоматически.

Этот документ фиксирует проектные решения, а не доказательство реализации. RED/GREEN, CI, реальный WebSocket, спрайты и browser acceptance ещё не выполнены. Изменение параметров по результатам acceptance оформляется отдельным явным решением; не подгонять тесты молча под реализацию.

Особые технические ограничения: компенсация RTT приблизительна, фактическое время физического тапа сервер доказать не может; под нагрузкой подтверждение дольше целевых 350 мс. В v1 используются server-derived timestamps, общий cap и пакетные размены, без обещания полной независимости от сети.
