# Ultimate Hockey — Еженедельный челлендж — дизайн-спецификация

**Дата:** 2026-05-31
**Статус:** дизайн согласован пользователем, готов к имплементационному плану

---

## 1. Контекст и цель

Еженедельный челлендж — отдельная недельная активность на второй странице приложения. Админ заранее создает челлендж, открывает вход для игроков, задает время начала и конца по Москве, набор обязательных заданий и награду. Игрок должен подтвердить участие. После старта челленджа его прогресс считается только за допустимый интервал участия.

Цель фичи — дать игрокам регулярную недельную цель поверх ежедневной игры, тренировок и дуэлей, не меняя механику самих режимов.

---

## 2. Скоуп MVP

В скоупе:
- Новый раздел второй страницы: **Еженедельный челлендж**.
- Отдельная страница челленджа.
- Админка для создания, редактирования, выбора активного челленджа и настройки награды.
- Только один активный челлендж одновременно.
- Допустимое состояние без активного челленджа.
- Подтверждение участия игроком.
- Обязательные задания внутри челленджа.
- Награда за выполнение всех заданий: монеты, звезды, опыт.
- Защита от повторного получения награды.

Не в скоупе первого шага:
- Формат "выполни любые N из M".
- Автоматическая генерация челленджей.
- Лидерборд участников челленджа.
- Push-уведомления о старте, завершении или награде.
- Сложный конструктор правил в стиле no-code.

## 3. Правила челленджа

### 3.1 Активность

В системе может быть не больше одного активного челленджа. Активность означает, что именно этот челлендж показывается пользователям в разделе и доступен через публичный API.

Если активного челленджа нет, на странице раздела показывается пустое состояние: "На этой неделе активного челленджа нет".

### 3.2 Время

Админ задает:
- `join_open_at` — с какого момента можно подтверждать участие;
- `start_at` — с какого момента задания начинают выполняться;
- `end_at` — когда челлендж заканчивается.

Все даты в админке вводятся и отображаются в московском времени. В БД храним `timestamptz`.

Публичные состояния вычисляются сервером:
- до `join_open_at`: вход еще закрыт;
- с `join_open_at` до `end_at`: игрок может вступить, если вход не отключен админом;
- с `start_at` до `end_at`: челлендж идет, задания доступны для выполнения;
- после `end_at`: челлендж завершен.

### 3.3 Участие

Игрок должен нажать **Участвовать**, чтобы его прогресс начал учитываться.

Прогресс игрока считается только с:

```text
progress_from = max(challenge.start_at, participant.joined_at)
```

Примеры:
- игрок вступил до старта — прогресс считается со старта;
- игрок вступил после старта — прогресс считается с момента вступления;
- действия до вступления не учитываются;
- действия до `start_at` не учитываются.

### 3.4 Задания

Все задания челленджа обязательные. Челлендж считается выполненным только если достигнуты цели по всем заданиям.

Типы заданий MVP:
- `goals_scored` — забросить N шайб;
- `duels_played` — сыграть N дуэлей;
- `duels_won` — победить в N дуэлях;
- `duel_invites_sent` — пригласить на дуэль N соперников;
- `trainings_completed` — завершить N тренировок.

Каждое задание имеет:
- тип;
- цель числом;
- порядок отображения;
- пользовательское название или серверный дефолтный текст.

### 3.5 Награда

Награда задается в админке при создании/редактировании челленджа:
- монеты;
- звезды;
- опыт.

Когда все задания выполнены, на странице появляется кнопка **Получить награду**.

По клику сервер:
1. Проверяет, что пользователь участвует в челлендже.
2. Проверяет, что челлендж активен или завершен, но награда еще доступна.
3. Пересчитывает прогресс по всем заданиям.
4. Проверяет, что все задания выполнены.
5. Начисляет монеты, звезды и опыт.
6. Записывает `reward_claimed_at`.

Повторное получение награды невозможно.

## 4. Данные

### 4.1 `weekly_challenges`

Основная таблица челленджей.

Поля:
- `id uuid primary key`;
- `title text not null`;
- `description text not null default ''`;
- `join_open_at timestamptz not null`;
- `start_at timestamptz not null`;
- `end_at timestamptz not null`;
- `is_active boolean not null default false`;
- `join_enabled boolean not null default true`;
- `reward_coins integer not null default 0`;
- `reward_stars integer not null default 0`;
- `reward_xp integer not null default 0`;
- `created_by uuid references users(id)`;
- `created_at timestamptz not null default now()`;
- `updated_at timestamptz not null default now()`.

Ограничения:
- `join_open_at <= start_at`;
- `start_at < end_at`;
- неотрицательные награды;
- partial unique index на единственный активный челлендж: `WHERE is_active = true`.

### 4.2 `weekly_challenge_tasks`

Задания внутри челленджа.

Поля:
- `id uuid primary key`;
- `challenge_id uuid not null references weekly_challenges(id) on delete cascade`;
- `type text not null`;
- `title text`;
- `target integer not null`;
- `sort_order integer not null default 0`;
- `created_at timestamptz not null default now()`.

Ограничения:
- `target > 0`;
- `type` в списке поддерживаемых типов.

### 4.3 `weekly_challenge_participants`

Участники челленджа.

Поля:
- `id uuid primary key`;
- `challenge_id uuid not null references weekly_challenges(id) on delete cascade`;
- `user_id uuid not null references users(id) on delete cascade`;
- `joined_at timestamptz not null default now()`;
- `reward_claimed_at timestamptz`;
- `created_at timestamptz not null default now()`.

Ограничения:
- `unique (challenge_id, user_id)`.

Прогресс не хранится как источник правды. Сервер считает его из игровых таблиц при запросе состояния и перед выдачей награды.

## 5. Источники прогресса

Прогресс считается сервером по существующим данным за интервал:

```text
[max(challenge.start_at, participant.joined_at), challenge.end_at]
```

Источники:
- голы: завершенные броски в игровых сессиях с результатом гола;
- сыгранные дуэли: завершенные дуэли, где пользователь был участником;
- победы в дуэлях: завершенные дуэли, где пользователь победил;
- приглашения в дуэль: созданные пользователем приглашения;
- завершенные тренировки: тренировки, которые дошли до критерия завершения.

Если в текущей схеме для конкретного источника не хватает надежного поля, реализация должна добавить минимальное событие/лог именно для этого источника, а не размазывать учет по фронту. Клиент не является источником правды для прогресса челленджа.

## 6. API

### 6.1 Публичные роуты

`GET /weekly-challenge/current`

Возвращает:
- активный челлендж или `null`;
- публичное состояние: `not_open`, `join_open`, `running`, `finished`;
- участие текущего пользователя;
- задания;
- прогресс пользователя, если он участвует;
- награду;
- доступные действия: canJoin, canClaimReward.

`POST /weekly-challenge/:id/join`

Подтверждает участие пользователя. Доступно, если:
- челлендж активен;
- вход открыт по времени;
- `join_enabled = true`;
- челлендж не завершен;
- пользователь еще не участвует.

Повторный join возвращает текущее участие без ошибки или безопасную 409-ошибку, выбранный вариант фиксируется в имплементационном плане.

`POST /weekly-challenge/:id/claim-reward`

Начисляет награду после повторной серверной проверки выполнения всех заданий.

### 6.2 Админские роуты

В существующий admin API добавляются роуты:
- `GET /admin/weekly-challenges` — список челленджей, включая прошлые;
- `POST /admin/weekly-challenges` — создать челлендж с заданиями и наградами;
- `PATCH /admin/weekly-challenges/:id` — изменить основные поля, задания и награды;
- `POST /admin/weekly-challenges/:id/activate` — сделать челлендж единственным активным;
- `POST /admin/weekly-challenges/:id/deactivate` — отключить активность;
- `POST /admin/weekly-challenges/:id/join-enabled` — включить/выключить вход.

Все админские действия требуют существующей проверки admin-role.

## 7. Web UI

### 7.1 Вторая страница

В `SectionsScreen` добавляется карточка **Еженедельный челлендж**. Визуально она следует стилю остальных разделов: изображение/обложка, название, короткий статус.

Статусы на карточке:
- нет активного челленджа;
- вход открыт;
- челлендж идет;
- завершен, если активный челлендж уже закончился.

### 7.2 Страница челленджа

Новая страница `/weekly-challenge`.

Состояния:
- загрузка;
- нет активного челленджа;
- активный челлендж без участия;
- активный челлендж с участием до старта;
- активный челлендж идет;
- челлендж завершен;
- все задания выполнены, награда доступна;
- награда получена.

Основной контент:
- название;
- описание;
- даты;
- награда;
- кнопка **Участвовать**, если доступно;
- список обязательных заданий с прогрессом;
- кнопка **Получить награду**, если доступно.

### 7.3 Админка

В `AdminScreen` добавляется раздел **Еженедельные челленджи**.

MVP-форма:
- название;
- описание;
- даты в московском времени;
- награды: монеты, звезды, опыт;
- список заданий: тип + цель + название;
- `join_enabled`;
- действие "Сделать активным".

При активации нового челленджа предыдущий активный автоматически выключается на сервере в одной транзакции.

## 8. Ошибки и крайние случаи

- Нет активного челленджа: публичный API возвращает `challenge: null`.
- Игрок пытается вступить после `end_at`: 409 с понятным кодом.
- Игрок пытается получить награду до выполнения всех заданий: 409.
- Игрок пытается получить награду повторно: 409 или idempotent response с `reward_claimed_at`, выбирается в плане реализации.
- Админ создает челлендж без заданий: 400.
- Админ задает некорректные даты: 400.
- Админ активирует челлендж: сервер в транзакции отключает остальные активные.

## 9. Тестирование

Server:
- создание челленджа админом;
- запрет пустого списка заданий;
- единственный активный челлендж;
- join до старта;
- join после старта;
- прогресс считается с `max(start_at, joined_at)`;
- действия до вступления не учитываются;
- выдача награды только при выполнении всех заданий;
- повторная выдача награды невозможна;
- все типы заданий считают корректный прогресс.

Web:
- карточка раздела на второй странице;
- пустое состояние без активного челленджа;
- вступление в челлендж;
- отображение прогресса заданий;
- состояние доступной награды;
- состояние полученной награды;
- базовый сценарий админки: создать, активировать, выключить вход.

Интеграционно:
- создать челлендж в админке;
- вступить пользователем;
- сгенерировать игровые события;
- проверить прогресс;
- получить награду и увидеть изменение баланса/опыта.

## 10. Открытые решения для имплементационного плана

Эти пункты не меняют продуктовую механику, но должны быть выбраны в плане:
- точные SQL-источники для каждого типа задания по текущей схеме;
- idempotent или 409-поведение для повторного join и повторного claim;
- формат дат в админской форме;
- нужна ли отдельная обложка для карточки раздела на первом релизе или используем существующий стиль/заглушку.
